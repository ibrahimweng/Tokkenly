# Tokkenly — marketing site

Thirteen static pages and one serverless function. No framework and no build
step: what is in this folder is what is served.

```
index.html          the landing page, written by hand
products/*.html     six product pages      ← generated by build-products.mjs
about.html …        about, blog, contact,  ← generated by build-pages.mjs
                    terms, privacy, 404,
                    sitemap.xml, robots.txt
styles.css          the product's light theme, applied to a website
site.js             the bar, the two menus, the reveals, the landing page's
                    moving parts, the blog's chips and the two forms
api/contact.js      the contact form and the newsletter, sent on through Resend
img/  fonts/        the pictures, and Geist
copy.txt            the landing page copy, as the page carries it
copy-*.mjs          the words of the generated pages
build-*.mjs         the generators
```

## Where it comes from

**The words** on the landing page are the client's landing page copy. The
Figma frames and the site's own reviews have since changed some of it on
purpose — four product cards where the document had six, the frames' wording
for three sections, sentence case for product names — and `copy.txt` carries
the page as it now stands. Its header names the commits that made each
change; its first version in git is the document as delivered.

**The layout** of every page is its Figma frame, measured at 1920 and held as
shares of the 1520 column, so a composition keeps its shape at any desktop
width and restacks below 1040.

**The colour** is the product's own light theme, lifted from
`app/src/styles/tokens.css` rather than picked again — the same canvas, ink,
accent, and sand. **The type** is the product's own face, Geist, and nothing
but it.

## The generated pages

The six product pages are built from `copy-products.mjs`: each product is a
name, a one-line promise, and `sections`, the page band by band in the order
its frame draws it. The company and legal pages, the 404, the sitemap and
robots.txt are built from `copy-pages.mjs`. Both builders share one nav, one
footer and one `<head>`, so a routing change is made once.

```bash
node site/build-products.mjs            # write the six product pages
node site/build-pages.mjs               # write the rest
node site/build-products.mjs --check    # write nothing; fail if a committed
node site/build-pages.mjs --check       # file is not what the builder makes
```

The output is committed, so an edit made by hand to a generated file lasts
until the next person runs the builder. Edit the copy or the builder and
regenerate; `--check` is what catches the other kind of edit.

Every internal link is extensionless — `/about`, `/products/convert` — because
Vercel's `cleanUrls` answers `/about.html` with a 308 to `/about`. Every band
on a product page has an id, `s-<name>` (`#s-faq`, `#s-steps`), and the hero's
"See how it works" goes to `#more`, just after the hero.

## Running it

Any static server that does clean URLs, as Vercel does:

```bash
npx serve site -l 4321     # http://localhost:4321 — /about serves about.html
```

`python3 -m http.server` does not map `/about` to `about.html`, so the links
will 404 under it. No static server runs `api/contact.js`; `vercel dev` does,
or post to the function from a test with a stand-in for Resend.

## Checking it

Nine scripts in `app/scripts`, in the manner of the suites that check the app,
sharing `_sitelib.mjs`. They drive a real browser against the served site at
`SITE_URL` (default `http://localhost:4321`), fail on any response that is not
2xx, and exit non-zero on any FAIL.

```bash
node scripts/_sitecheck.mjs      # the landing page at 1440/834/390: broken
                                 # images, overflow, errors, failed requests
node scripts/_sitecopy.mjs       # every line of copy.txt is on the page
node scripts/_sitecta.mjs        # every page's closing slab places its art
node scripts/_sitegs.mjs         # the Getting started mocks play as scripted
node scripts/_siteinteract.mjs   # the menus, the accordion, the blog's chips,
                                 # the forms (with the function stood in for)
node scripts/_siteprod.mjs       # the builders' --check, no personal address
                                 # anywhere served, every page clean at three
                                 # widths, every link and #anchor resolves

# pictures, not checks
node scripts/_siteshots-gs.mjs   # Getting started, before and after (SITE_URL
                                 # and SITE_BEFORE_URL, two builds)
node scripts/_siteshots.mjs      # photograph the app for the site, against a
node scripts/_siteopt.mjs        # built app on :4173, and re-encode to WebP
```

`_siteshots.mjs` and `_siteopt.mjs` write into `site/img`. Nothing they take
is on the site at the moment; they are kept for the day it wants screenshots
of the app again.

## Deploying

The app and the site both live on `main` and deploy from it, to two
addresses, as two Vercel projects pointed at different folders:

| Vercel project | Root Directory | Reads | Serves |
|---|---|---|---|
| the app | repository root | `vercel.json` | `cd app && npm run build` → `app/dist` |
| the site | `site` | `site/vercel.json` | this folder, as it stands, and `api/` |

To add the site: **Add New → Project**, import the same repository, set
**Root Directory** to `site`, framework preset *Other*, no build command and
no install command. Vercel's Root Directory picker only lists folders that
exist on the default branch, so `site/` has to be on `main` first.

`site/vercel.json` names an install command and a build command even though
there is nothing to install or build, and both are `echo`. A key left out of
`vercel.json` falls through to whatever the project has saved in its
dashboard, and a project made from this repository can easily be holding the
app's `cd app && npm ci` there — which fails from inside `site/`. Saying both
explicitly closes that door.

### The contact function

`api/contact.js` deploys as a Vercel function on its own: files under `api/`
are functions whatever the build settings say. It needs, on the site's
project (**Settings → Environment Variables**):

| Variable | Value |
|---|---|
| `RESEND_API_KEY` | a Resend API key. Without it the function answers 503 and both forms tell the visitor to email support@tokkenly.com instead. |
| `CONTACT_TO` | where messages are delivered. Defaults to `ibrahimweng0@gmail.com`, the mailbox mail actually reaches. |

Mail is sent from `support@tokkenly.com`, so **tokkenly.com must be a verified
sending domain in Resend** (its DNS records added) before anything leaves.
The visitor's address is the Reply-To. The function validates the fields,
drops anything that fills the hidden honeypot, and limits each address to
five messages in ten minutes — per function instance, which is a speed bump
rather than a wall.

`CONTACT_TO` is configuration. The address a visitor sees, on every page and
in every message, is `support@tokkenly.com`; `_siteprod.mjs` fails if any
other address appears in anything the site serves.

### Headers, caching and what is served

`site/vercel.json` sends a Content-Security-Policy on every response that
allows scripts, fonts, images and requests from the site itself only, and
inline styles (the generated pages position their art with `style=`
attributes). There is no inline script. Alongside it: `nosniff`,
`strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, a minimal
Permissions-Policy and HSTS.

Images and fonts are cached for a day and revalidated in the background for a
week. They are not `immutable`: file names here are reused when a picture is
re-exported, and a year-long immutable cache would keep serving the old one.

The folder deploys as it stands, so `.vercelignore` keeps the sources out of
it: this README, `copy.txt`, the `.mjs` generators and copy files.

### The domain

Canonical links, `og:url`, `og:image`, the sitemap and robots.txt all assume
the site is **https://tokkenly.com**. Nothing in the repository stated the
domain; if it is different, change `SITE_URL` in `copy-products.mjs` and the
four absolute URLs in `index.html`'s head, and regenerate.

## Still to come

- **Terms and Privacy are drafts.** They describe what the product actually
  does in plain language, say at the top that they are under legal review,
  and carry `noindex` (and are left out of the sitemap) until counsel's text
  replaces them. The final version has to add what the draft names as missing:
  the company, its licences, the dispute route, retention periods.
- **The blog has no posts.** The six cards are the posts that are coming, and
  say so; the chips filter them. When one is written it becomes a link.
- **No social accounts.** The footer's X, Instagram and LinkedIn icons are
  gone until there are profiles to link to.
